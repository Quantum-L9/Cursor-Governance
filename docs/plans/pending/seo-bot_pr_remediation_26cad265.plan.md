- Its CI failure (`TS2459` on `FullSiteQAConfig`/`VisualQATask` from `@quantum-l9/llm-router`) is not a live bug. Diffing its `src/services/llm.ts` against `origin/main`'s version shows main already fixed this by importing those types from the `@quantum-l9/llm-router/vision` subpath; PR #35's stale copy still imports them from the bare package (the old, broken pattern). ## The one real, still-open gap found on current `main`

- `.github/workflows/ci.yml` still runs `npm install --no-audit --no-fund` with a comment claiming *"No committed lockfile yet, so use `npm install` (not `npm ci`)."* That comment is now false: `package-lock.json` exists on `origin/main` (shipped by the assurance PRs). ADR-0007 (`accepted`) explicitly decided on "npm 10 and a committed package lock" for reproducibility -- but the CI workflow itself was never switched over, so the lockfile is committed but not actually enforced.
- Not currently causing a visible failure (main's last push-triggered CI run succeeded, and current dependency resolution happens to still satisfy the code), but it's a real, verifiable misalignment between an accepted ADR and executable CI, and it's exactly the kind of silent-drift risk ADR-0007 exists to close (a future semver-range dependency bump could break CI exactly the way PR #35's stale snapshot did, just for real).

### Fix

- In `.github/workflows/ci.yml`: change the install step to `npm ci --no-audit --no-fund` and delete the now-stale "no committed lockfile yet" comment block.
- Validate locally before proposing: `npm ci`, `npx tsc --noEmit`, `npx vitest run` against current `origin/main` to confirm nothing breaks under strict lockfile-pinned install.
