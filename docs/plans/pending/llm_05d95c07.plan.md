# LLM-Router PR Remediation Strategy (read-only findings + execution plan)

## 0. Critical context that reframes the whole plan

Branch protection on `main` requires only **3** status checks: `ESLint`, `tsc --noEmit`, `Vitest` (from [.github/workflows/l9-lint-test-node.yml](.github/workflows/l9-lint-test-node.yml)). Every other red check (semgrep/"L9 Analysis", `l9_governance`, `l9_scorecard`, `l9_pr_pipeline`, `l9_security`, `l9_pre_commit`, SonarCloud, CodeQL, and the extra jobs inside `l9-node-ts-monorepo.yml`) is **not required to merge**. Confirmed via `gh api repos/Quantum-L9/LLM-Router/branches/main/protection`.

Result: **12 of 14 open PRs are already `mergeable: MERGEABLE` / `mergeStateStatus: UNSTABLE`** (i.e., mergeable today despite red X's) — only `mergeStateStatus: BLOCKED` PRs are genuinely stuck. This changes the objective from "turn every checkmark green" to "(a) fix what's actually blocking merge, then (b) clean up the informational noise for governance hygiene," in that order.

## 1. Superseded PRs (identify before touching anything)

- **#4, #5, #6, #7** (dependabot) — all four touch only [.github/workflows/l9-analysis.yml](.github/workflows/l9-analysis.yml), each bumping one `Quantum-L9/l9-ci-core` action ref from `54a2f2fc...` → `d2c2cd7f...` (validate-bundle, build-artifact-manifest, provision-sdk, publish-analysis.yml respectively). **PR #2 already bumps every one of those exact lines further, to `89dcb36e...`**, in its commit `fix(ci): bump stale l9-ci-core pin to unblock Analyze (semgrep -> SDK)`. Once #2 merges, #4/#5/#6/#7 become no-op/conflicting diffs — Dependabot will auto-detect and close them on its next scan. **No manual close needed if #2 merges first; do not merge #4-#7 independently (they'd immediately regress the pin).**
- **#2 vs #16** — not a clean supersession, a *two-way* overlap:
  - #16's commit `260040853` ("Merge fix/unified-remediation-phases-1-7 into feature branch (Phase 0)") already merged #2's branch into #16 at 07:22 — so all 18 audit-finding fixes from #2 exist inside #16.
  - But #2 kept progressing *after* that merge point with 2 more commits (`026cbeb`, `175d713`) that fix the semgrep/SDK pin and a `publish-analysis.yml` follow-up. **#16 does not have these two commits** — confirmed: #16's current "Analyze (semgrep -> SDK)" check still fails with the *old* pin (`54a2f2fc`) and the same `ModuleNotFoundError: No module named 'yaml'` that #2 already fixed.
  - **Recommendation: merge #2 into `main` first** (it is the smaller, fully-required-checks-green PR), **then update #16's branch** (merge/rebase `main`) to inherit the 2 missing CI-fix commits. Do not discard either PR's content.
- **#8, #9, #10, #11, #12, #15** — independent single-dependency bumps (`upload-artifact`, `pino`, `@types/node`, `eslint`, `openai`, `vitest`). Confirmed no file/line overlap with each other or with #2/#16. Not superseded.

## 3. The two genuinely-blocked PRs (RC7 detail)

- **#13** `typescript` 5.9.3 -> 7.0.2: `npm ci` fails — `typescript-eslint@8.64.0` peer-requires `typescript ">=4.8.4 <6.1.0"`. TS 7 is not yet supported by the installed `typescript-eslint`.
- **#14** `zod` 3.25.76 -> 4.4.3: `npm ci` fails — `openai@4.104.0` has `peerOptional zod "^3.23.8"`. Zod 4 is not yet supported by the installed `openai` SDK version (note: **#12**, open in this same PR set, bumps `openai` to 6.48.0 — need to check whether openai 6.x supports zod 4 before resolving #14).

Both are legitimately un-mergeable today; recommend hold, do not force-merge, until upstream (`typescript-eslint` or `openai`) ships compatible ranges, or until #12 lands and is confirmed to lift the zod constraint.

## 4. Priority-ordered remediation sequence (unblock CI-green, cheapest/highest-leverage first)

Each numbered item is one remediation cycle (per l9-pr-remediation protocol: local-verify before push, one push per cycle, reply+resolve every thread). No step here is executed without your separate go-ahead per PR — this is the plan only.

1. Merge PR #2 (`fix/unified-remediation-phases-1-7`) into `main`. It already passes all 3 required checks; only non-required SonarCloud (RC6) and the RC1 legacy-pin fix (already resolved by #2 itself) are outstanding. This is the single highest-leverage merge: it (a) lands the semgrep/SDK pin fix (RC1) for every future PR built off new `main`, (b) obsoletes #4/#5/#6/#7 automatically.
2. Verify Dependabot auto-closes #4, #5, #6, #7 after #2 lands (their target lines will already be past the version they're bumping to). If Dependabot doesn't auto-close within its next scan window, close them manually with a comment pointing to #2's commit as the superseding fix.
3. Rebase/update PR #16 onto the new `main` (post-#2) to inherit the 2 missing CI-fix commits (`026cbeb`, `175d713`). Re-run local verify (`npm run build && npm run verify:types && npm run lint && npm test`) after the merge to confirm no regressions, then push once.
4. Fix RC6 (SonarCloud Security Rating) on #16's branch (and it'll already be moot on #2 once merged): add `--ignore-scripts` to the 5 flagged `npm ci` lines; pin `pip install semgrep==1.170.0` in `l9-analysis.yml`. This is the only remaining item keeping #16's SonarCloud gate red, and it's a 6-line, zero-risk change.
5. Merge #8, #9, #10, #11, #12, #15 (independent dependency bumps) — each is already `UNSTABLE`/`MERGEABLE` today; no code change needed, just a merge decision per PR once you're comfortable with the non-required noise.
6. Decide on RC2/RC3/RC4/RC5 (the Python-governance-template family) — these need a maintainer decision, not a code fix, because they assume infrastructure (`l9-ci` PyPI package, valid scorecard-action tag, Python governance config, pre-commit Python hooks) that doesn't exist for this Node/TS repo. Two honest options:
   - (a) Minimal-viable-green: add the missing placeholder files the same way PR#16 already did for `requirements.txt` (empty `requirements-ci.txt` for RC4) and accept that `l9_governance`/`l9_security`/`l9_scorecard`/`l9_pre_commit` will keep failing on the parts that need the actual `l9-ci` package / valid scorecard tag (external, not fixable here) — document each as a filed issue against `Quantum-L9/l9-ci-core`.
   - (b) Scope-down: since these checks are not required for merge anyway, stop treating them as CI signal for this repo (request the reusable-workflow caller be removed/disabled for LLM-Router) until `l9-ci-core` publishes a working Node/TS profile.
7. Hold #13 and #14 (RC7) — do not merge until `typescript-eslint` supports TS 7 or `openai`'s installed range supports zod 4. Recheck after #12 (`openai` 4->6.48.0) lands, since that may change the zod peer range.
8. File an upstream issue against `Quantum-L9/l9-ci-core` consolidating RC1 (now fixed forward, but worth flagging the missing `requirements.txt` install step upstream too), RC2 (unpublished `l9-ci` package), RC3 (invalid scorecard-action tag) — one issue, all three, since they're all "reusable-template correctness" bugs outside this repo's ownership.

## 5. What this plan deliberately does NOT do

- No merges, closes, rebases, or pushes executed yet — this is findings + sequencing only, per the "no destructive actions" instruction.
- No fabricated Python governance scaffolding (`.github/governance/*.yaml`, fake ruff/mypy pre-commit hooks) to force RC5's checks green — that would violate "no silent placeholders" and paper over a real infra gap with theater.
- No attempt to force-resolve #13/#14 by pinning to `--legacy-peer-deps` or `--force` — that would silently mask real incompatibility rather than fix it.
